## 1. Arquitetura
- **Backend:** `source/server.py`, Python 3.8 (biblioteca padrão), `ThreadingHTTPServer` em **127.0.0.1** (porta preferida 8765, varre 8765–8780 e depois porta livre; `server.json` em `~/.eiah-aws/dashboard-state/`). Nada de CDN, fontes externas, analytics ou hospedagem externa.
- **Frontend:** `source/index.html`, `app.css`, `app.js` (HTML/CSS/JS puros, português, claro/escuro, responsivo). Todo texto vindo do servidor entra no DOM por `textContent`; CSP `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'`.
- **Fontes de dados (somente leitura):** `systemctl --user show` (timers e serviços), `loginctl show-user` (Linger), `timedatectl show`, `df`, `STATE`/`KIND`/`run.json`/`receipts.tsv`/`uploaded.tsv`/`state/*`/`receipts.superseded.tsv` de cada run em `~/.eiah-aws/backup-a-auto/queue/` e, como fonte configurada, as capturas manuais G3 (`~/.eiah-aws/backup-a/BACKUP-A-*`, com o registro de upload do G5 em `BA_BASELINE_G5_OBJECTS`), `alerts/`, logs com leitura limitada (últimos 16 KB). Configuração lida de `backup-a.env` **sem executá-lo**. Hashes mostrados são os registrados nos recibos (nenhum hash de backup é recalculado). `backup-a.sh status` não é usado nas consultas porque executa `mkdir`/`chmod -R` ao iniciar; a regra de fila (soma dos runs que não estão em UPLOADED_VERIFIED, mesma do script) foi conferida contra o `status` (testes e `validation/real-data-checks.txt`).
- **Tempo:** cada instante é convertido por `date` + tzdata (`TZ=America/Sao_Paulo` e `TZ=UTC`), nunca por subtração; ISO-8601 com offset explícito (`2026-10-17T08:00:00-03:00 (America/Sao_Paulo)` e `2026-10-17T11:00:00Z (UTC)`), com o texto original no `title`. AGENDADO, disparo, início real, término e consulta são campos distintos.
- **Atualização:** o navegador consulta `/api/overview` a cada 5 s com `setTimeout` encadeado (sem sobreposição); mostra a idade da última tentativa e da última atualização bem-sucedida, "DADOS DESATUALIZADOS" após 15 s e erros por fonte; fonte indisponível vira `não disponível` (nunca 0/vazio). No servidor há cache de 2 s. Fechar a página ou parar o servidor não interrompe timers, capturas ou uploads.

## 4. Upload manual controlado (implementado; não executado)
1. Owner abre um run em CAPTURED/UPLOADING (botão "Enviar este run ao S3").
2. **Plano:** `backup-a.sh upload --plan --run RUN --full-verify` (sem AWS) → run, objetos pendentes, bytes, bucket/região, chaves de destino, SHA-256, verificação completa; hash do plano (inclui estado, chaves, bytes, SHA-256, `receipts.tsv`, hash de `backup-a.sh` e `backup-a.env`). Opcional "Conferir no S3" (HeadObject pela Restore, só com sessão válida; chave existente bloqueia).
3. **Confirmação explícita** digitando `ENVIAR <RUN>`, com sessão AWS verificada há ≤ 15 min por ação explícita.
4. **Execução:** o backend consome o plano (uso único), **recalcula** o plano e compara o hash (se mudou ⇒ 409 "revise e confirme novamente"), exige que nada esteja rodando (job do dashboard, captura/upload/conciliação por `pgrep`) e executa **apenas** `backup-a.sh upload --run RUN --full-verify` (mesmo uploader: `--if-none-match '*'`, SHA-256, `AWS_MAX_ATTEMPTS=1`, sem repetição cega; verificação por download completo pela Restore; UPLOADED_VERIFIED só após todos os objetos).
5. **Acompanhamento:** job persistido em `~/.eiah-aws/dashboard-state/jobs/`; a interface lê estado/log do servidor; o veredito vem dos recibos (um exit 0 sem UPLOADED_VERIFIED, p.ex. por lock, é "NADA CONFIRMADO"). 412/ambíguo seguem o procedimento existente (`reconcile` somente leitura, com confirmação).
6. **Duplo clique/repetição:** plano de uso único, trava global de job e checagem de processos; o processo do upload roda em sessão própria — fechar a página não o cancela nem repete; se o servidor reiniciar, o job vira `running_untracked`/`indeterminate` ("INDETERMINADO até reconciliar os recibos").
Lock: preparar plano chama `upload --plan`, que segura o lock do BACKUP-A por ~1 s; evite 08:00 diário e sexta 18:00.

## 5. Autenticação AWS
O dashboard exibe o comando real de login (`source ~/.eiah-aws/env.sh` + `BROWSER=~/.eiah-aws/open-after-listener.sh eiah_aws login --profile <IAM_PROFILE_OPERATOR_LOGIN> --redirect-port 34977`) para o owner executar no terminal; não recebe senha, MFA, token nem URL; não inicia login; não guarda credenciais. "Verificar sessão AWS" só por clique: `sts get-caller-identity` nos três perfis, com horário da consulta; o resultado é mostrado como foto daquele instante (idade em minutos; "ANTIGA" após 15 min). A atualização automática não chama AWS (testado). Sem sessão válida o envio é bloqueado.

## 6. Segurança do serviço
Bind exclusivo 127.0.0.1; Host estrito (`127.0.0.1:porta`/`localhost:porta`); POST exige Origin igual, token de sessão (cabeçalho `X-BA-Token`, nunca em URL/log/armazenamento do navegador) e `application/json` ≤ 4 KB; sem CORS; métodos PUT/DELETE/PATCH/OPTIONS = 405; rotas fixas, nenhuma leitura de arquivo arbitrário ou path traversal; ids de run validados por regex e pelo inventário; subprocessos só por lista de argumentos (sem shell); `access.log` só com método e caminho; `actions.log` registra ações manuais sem segredos. Limitação: o token é entregue a qualquer cliente local que consiga `GET /api/session` com Host válido (processos do mesmo usuário/Windows na máquina); o modelo protege contra páginas web de outras origens e DNS rebinding, não contra malware local.

## 8. Operação
`backup-a-dashboard start|stop|status|url|open|run` (`~/.local/bin/backup-a-dashboard` → `dashboard/backup-a-dashboard.sh`). Iniciar: `backup-a-dashboard start` (em segundo plano, setsid); abrir no navegador do Windows: `backup-a-dashboard open`; parar: `backup-a-dashboard stop` (não afeta timers/capturas/uploads). `backup-a-panel` continua funcionando (testado). Nenhuma inicialização automática, do terminal ou do Windows, foi configurada.

## 9. Como registrar em evidência os futuros uploads feitos pelo dashboard
Aparecer no painel **não** equivale a estar indexado. Após um upload: (1) conferir no detalhe do run o estado `UPLOADED_VERIFIED`, `download-completo` e VersionIds; (2) criar `ops/evidence/latest/backup-a-upload-run-<sufixo>-<data>/` com `UPLOAD.md`, cópia de `uploaded.tsv`, `receipts.tsv`, `api/*.put.json|get.json`, o log do run e a saída do `audit`, com horários UTC e Brasília; (3) gerar `MANIFEST.sha256` (`sha256sum`); (4) acrescentar a entrada em `docs/EVIDENCE_INDEX.md` seguindo o padrão e citando os hashes; (5) rodar `pnpm check:evidence-index`. O log de ações do dashboard (`~/.eiah-aws/dashboard-state/actions.log`, `jobs/`) é apoio, não substitui os recibos.

## 10. Limitações
Upload real pelo botão e a conciliação real não foram exercitados (só doubles); o histórico cobre apenas fontes locais (nada do S3); a validade de uma sessão AWS pode mudar depois da verificação; `reconcile` existente age sobre toda a fila (somente leitura no S3); sincronização externa do relógio permanece NÃO COMPROVADA; `Linger=no`; o dashboard só roda enquanto o servidor estiver iniciado (sem inicialização automática).
